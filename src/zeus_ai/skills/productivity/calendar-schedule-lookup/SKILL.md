# Calendar schedule lookup

Read-only schedule lookup through whichever calendar sources this install has: the configured calendar snapshot (see zeus-calendar), Google Calendar through Composio, the `gog` CLI, and Apple Calendar on a Mac. Use the ones that are set up; a source that is not configured is missing coverage, not an empty calendar. Preserve the existing scheduling and task owners. Do not create events, reminders, tasks, background jobs, another calendar store or a scheduling engine.

## Fix the question before reading
- Use the current date in the owner's timezone (`owner.timezone` in the Zeus config, called TZ below) for relative questions. "This week" is Monday through Sunday; "next week" is the following Monday through Sunday. "Next seven days" is rolling. For an explicit date range keep those exact dates. State the inclusive dates once in the answer.
- Record one original window: local start midnight inclusive, next local midnight after the final date exclusive, and TZ. Compute the two offsets separately using that named timezone. A week across daylight-saving can be 167 or 169 elapsed hours. Do not paste one offset onto both ends. Do not extend or move the window to get a nonempty result.
- Use overlap: event start < exclusive window end AND event end > window start. Events ending exactly at the start and starting exactly at the end are outside. Keep events already in progress.

## Prove what was read
- Check every configured source (Google and Apple when both exist). Inventory currently connected accounts, including unavailable/signed-out accounts and previously known calendars. Use current connector discovery, not a historical account list as completeness proof. Do not start a connection, consent flow or token repair without authorization. No events from a failed source means unknown, not empty.
- For each readable Google account enumerate its calendar list, including hidden calendars where supported. Follow every calendar-list continuation token until absent. Keep account ID plus calendar ID; names are not identities. A failed inventory leaves that account's coverage unknown even if some calendars worked.
- Discover and inspect the complete current tool schemas. With Composio, use COMPOSIO_SEARCH_TOOLS then COMPOSIO_GET_TOOL_SCHEMAS as needed. Prefer GOOGLECALENDAR_LIST_CALENDARS with show_hidden true and page_token. For each calendar use GOOGLECALENDAR_EVENTS_LIST with timeMin/timeMax equal to the original window, timeZone TZ, singleEvents true and pageToken for later pages. Keep all filters and the original window unchanged across pages. Retain continuation fields if selecting fields. An empty page with a token is not the last page. Stop a repeated token as incomplete coverage rather than looping.
- GOOGLECALENDAR_EVENTS_LIST_ALL_CALENDARS may be useful for an initial view. Its current schema does not expose a continuation input, while its documentation warns about pagination. One unified result, a successful flag, no errors_by_calendar, or a count below a limit does not prove every calendar/page was read. Use the paged per-calendar route for completeness. If it is unavailable, disclose the gap; never invent a token argument. Read errors_by_calendar, calendars_queried and minimal summary_view versus full events carefully. Do not count summary_view and events as two copies of every event.
- gog fallback is read-only. First enumerate accounts/calendars; use --readonly --json calendar events --all --all-pages with explicit original --from/--to bounds for each account. Do not use --results-only or a field selector that removes continuation/coverage information. A primary-only result is not every calendar. A failure or timeout remains missing coverage.
- Apple: copy scripts/apple_calendar_range.applescript to scratch, set START_YEAR/START_MONTH/START_DAY/DAY_COUNT to the original dates and run bounded with perl -e 'alarm 120; exec @ARGV' osascript <copy>. Set EXPECTED_ZONE to TZ as well: the adapter requires the Mac's named timezone to match it. A different zone is an unavailable read; do not change the Mac's timezone. Keep the WINDOW header and final READ COMPLETE marker. Missing markers, a mismatched window, timeout, a nonzero exit, ERROR lines, nonzero identity_failures/identity_unverified_rows, identity=unverified rows, or unexpanded recurring series mean incomplete coverage. Optional stable-ID property failures preserve otherwise readable rows with empty unknown ID fields and identity=unverified; do not treat these rows as confirmed unique events, invent IDs, merge by title/name/time, or discard the source information. This also applies to recurring-series definitions, which remain unverified until an existing source confirms actual occurrences. A recurring series is not a confirmed occurrence. Verify occurrences through an existing source or leave them unverified; do not infer free time from the range pass alone. Even a completed Apple read reports unverified_local_cache: it cannot prove server freshness or that a disconnected account is current. Do not claim a sign-in expired without evidence.

## Preserve dates, identities and known items
- All-day date values are local calendar dates with an exclusive end date. Do not parse YYYY-MM-DD as UTC or shift the displayed day. Timed dateTime values must have an offset or a verified named event/calendar timezone. Unknown or ambiguous timezones remain unverified; never guess a missing offset during the repeated daylight-saving hour. Sort timed items by their actual instants, then display in TZ. The two 1:30 times during fall-back can be different meetings.
- Keep account/calendar/event IDs and recurrence occurrence identity. Remove a repeated copy from the same source only with the same stable event ID and occurrence. Across calendars/accounts/providers, collapse copies only with a shared verified iCalUID (or equivalent stable cross-source identity), matching occurrence/start, end and all-day type, and no conflicting event details. Preserve source provenance. Same title/time or calendar name is insufficient. Conflicting copies stay separate and unverified. Do not merge different events.
- An empty or partial refresh must not erase previously known items. For the same original window, carry prior known items from failed/unread, truncated or stale sources as stale/unverified, separate from confirmed items. Do not call them cancelled or current. Only an explicit cancellation or a fresh complete authoritative source read can resolve that source's prior item. If prior state is unavailable, say it is unavailable; do not invent it. No new persistent calendar cache is requested.

## Answer plainly
Lead with any coverage gap that could change the answer: "I could read Work and Family, but the other account is signed out and Apple's saved copy is unverified. Here is what I could confirm for October 26 through November 1."
List confirmed items with day/date, time and title. Label all-day events, stale items and reminders accurately. Report which account/calendar coverage is missing once in everyday words. An empty partial read means "I could not confirm the full schedule," never "nothing scheduled," "quiet," "free" or "available." Keep script names, raw errors and tool details in the work record. Combine with the existing task workflow for priorities questions; this skill does not change task ownership or authorization.
