# Hotel rooms and restaurant tables

Use Zeus’s own browser and the existing purchase lock, which knows these two reservation providers. All helper commands below are relative to this installed skill. Use `python3 -B "$HERMES_HOME/skills/productivity/zeus-reservations/reservations.py"` as the command prefix. Adding anything to a calendar is a separate change that needs the owner’s own yes (see zeus-calendar).

1. Use the original message ID or stable task ID as KEY. Run `start KEY hotel` or `start KEY table`. Use `resume KEY` when the request returns. Respect changes, STOP and unresolved earlier submissions. Ask for the one missing fact that prevents meaningful research.
2. In Zeus’s normal browser, open [Trip.com hotel search](https://www.trip.com/hotels/) or [OpenTable](https://www.opentable.com/). On Trip.com select location, dates, number of rooms and guests, then choose the actual room and rate. Check both payment now and mandatory charges on site. On OpenTable pick the exact restaurant, date, local time, seats and party size. Check deposits, card guarantees and late-cancel or no-show charges. Read availability and terms for the **chosen** rate or table. Display competing options only with the provider source and separate prices for each.
3. Use ordinary, clearly nonbinding search, availability and review controls. If a control may commit a booking, treat it as final. At an actual review page, use `tabs` to identify the provider tab. Inspect that tab and identify the **unique enabled final control**, including its exact label. If a sign-in, account verification, app wall or missing terms interrupts the work, `pause KEY TAB sign-in` (also `app-only`, `missing-terms`, `unavailable`). Use the optional `--with-details` and a JSON object on stdin to preserve the chosen venue, date, time, seats, or room as unverified request details. Tell the owner exactly what is already prepared and where to continue on the original tab. Use the existing attended sign-in route when it supports this provider; otherwise the owner signs in themselves in the provider tab. No credentials or login codes in chat. Resume the same KEY and read the review again. Search snippets and listing prices cannot authorize a booking.
4. Run `prepare KEY TAB` with a JSON object on stdin. Fields are exact short visible quotes, including surrounding labels as needed. Common fields are `venue,location,date,party,selection,total,fees,policy,button`. Add `checkout` for a hotel or `time` for a table. Show full-stay currency and total, all excluded mandatory charges (include them in the owner explanation or hold if amount is unknown), cancellation terms and deadline. For a table, distinguish amount owed now from the cost of dining and no-show charge. An absent price is unknown. If the provider does not show the required evidence, keep the checkpoint and explain the missing fact. A returned status of `prepared` includes the exact `ask`. Send that text **as the entire message** in the owner’s verified private Zeus conversation. Native operator terminal, TUI and Hermes app replies work when the private gateway records the authenticated turn. Relayed messages and standalone terminal sessions without an identity receipt cannot approve. From those surfaces, use the owner’s established private Zeus chat (for example iMessage or a verified direct message) for the original offer so the owner only confirms once. Send it there through the existing authorized route and wait for their reply.
5. After the owner’s yes, reread the same final page and run `approve KEY TAB` with the current fields. Its code checks Zeus’s native owner conversation, original offer and provider page. `prepared` means the page changed: send the new exact ask and wait. `armed` permits a single click within two minutes. In the normal `browser_exec` tool, switch to the exact prepared tab and use **one** `click_element` on the matching final button. The native purchase lock rereads the live terms and checks the owner’s latest reply immediately before dispatch. Only the browser receipt records that a press occurred. A blocked button, browser failure or missing proof is reported honestly. Keep the lock active. Never retry an unknown submission.
6. Read the provider confirmation page or bookings list independently in the same account. Match venue, dates/time and party to the prepared reservation. Run `receipt KEY TAB` with `{"reference":"<visible confirmation number>"}` on stdin. A confirmed result is evidence of a booking. A timeout, a changed URL, payment processing page, blank account, screenshot of review or a local receipt of the click leaves `awaiting_receipt`. Use `resume` and read the provider. Never start a replacement while the original outcome is unresolved. If you have to exit at a genuinely app-only provider step, tell the owner which remaining action is theirs and verify the result from the provider if possible. Keep booking references private. Calendar exports use the trip itinerary skill.
7. `stop KEY` closes an unsubmitted preparation. After a submit it holds and calls for reconciliation. Any real cancellation or rebooking needs its own owner approval.

The helper stores only the selected fields, checkpoint, page fingerprint, approval reference and booking receipt under the Zeus profile. It reads visible page text in memory. Do not enter personal identifiers or credentials in the selected fields. A resumed tab may expire. Reopen the provider through the original search and prepare a fresh quote when it does.
